2. ROOT CAUSES
================================================================================
Nine RenameIndex  : migrations hardcoded index names; models declared no explicit
                    name, so Django derived different hash-based names.

facilities        : uniq_submitted_application_per_facility_kind was created by
                    facilities/0003_owner_media_integrity and enforces 06-DATA-MODEL,
                    but FacilityApplication had no Meta at all, so the autodetector
                    proposed dropping it. The project qualifier could not detect this:
                    it searched for the name inside the migration text, which keeps its
                    historic AddConstraint forever and therefore always matched.

pharmacy_duty     : pharmacy_duty/migrations/0001_initial declared its own local copy of
                    the TstzRange helper instead of importing pharmacy_duty.models.TstzRange.
                    Probe result:
                      TstzRange.deconstruct() round-trip : STABLE (d1 == d2, rebuilt == original)
                      model    class : pharmacy_duty.models.TstzRange
                      migration class: pharmacy_duty.migrations.0001_initial.TstzRange
                      same class     : False
                    BaseExpression.identity begins with self.__class__, so the two
                    expressions could never compare equal and the drift was perpetual.
                    Deconstruction was never the problem.

accounts          : PermissionsMixin field definitions in the hand-written migration
                    omitted verbose_name and help_text. Fields were present since
                    accounts/0001_initial; only their definition drifted.

10. INT-030 FOUND BY RUNNING ON POSTGRESQL FOR THE FIRST TIME
================================================================================
facilities/tests/test_owner_api.py::test_submit_rechecks_current_owner_registration_switch
  django.db.utils.NotSupportedError:
  FOR UPDATE cannot be applied to the nullable side of an outer join

submit_facility locked with select_for_update() over
select_related("category__group", "category__capabilities", "province").
category__capabilities is a reverse one-to-one, so select_related emits a LEFT OUTER
JOIN and PostgreSQL refuses FOR UPDATE on its nullable side.
POST /api/v1/owner/facilities/{id}/submit/ would have failed at runtime in every
environment. SQLite never enforced the rule, so the defect stayed invisible.

Fixed with select_for_update(of=("self",)): the intended lock on facilities_facility
is kept, the joined reference rows are not locked, semantics unchanged. The other
three select_for_update sites were checked and are unaffected.
